Polar — architecture & GRPO batch construction

How a training step turns into rollouts: trainer (Slime) → Polar Rollout server → Gateway nodes (per-session pipeline with runtime sandbox + LLM proxy + inference) → trajectories → GRPO-normalized samples back into Slime.

1 · System architecture

Training process (Ray + Megatron)

Builds prompts & group_index, calls generate_rollout_polar_async, applies post_process_rewards, then PPO/GRPO update.

Polar service plane

Gateway fleet · one process per node
gateway node localhost-01 :8100
Stage-isolated worker pools: INIT → READY → RUNNING → POST-RUN. Catch-all proxy route on the same port.
gateway node localhost-02 :8101
Heartbeats to rollout every heartbeat_interval_seconds. Drains gracefully on shutdown.
Inside one session (gateway-managed)
Runtime sandbox Docker / Apptainer
One container per session. Host session_dir bind-mounted at /polar/session. Prepare recipe (upload_file / upload_dir / exec) runs before the agent.
Agent harness unmodified agent
Started by harness preset (codex, claude_code, gemini_cli, …) or a shell/import_path. Polar injects: OPENAI_BASE_URL / ANTHROPIC_BASE_URL / GOOGLE_API_URL + *_API_KEY = session_id. The agent never knows Polar is in the loop.
LLM proxy gateway/proxy + transform/
detect API family → transform request to the served model → forward → capture CompletionRecord → transform response back. Streaming is synthetic SSE replay.
Inference server SGLang / vLLM
Single served model; gateway adds token-id / logprob params and canonicalizes responses. /admin/inference/pause + /resume gate generation during weight sync.
All cross-process traffic is HTTP. Cardinality: 1 trainer ↔ 1 rollout server ↔ N gateways ↔ N inference servers. The bridge package slime_bridge lives outside polar because Slime/Ray/Megatron are installed in the trainer environment only.

2 · Per-session pipeline (one of N samples)

Each TaskRequest with num_samples = G fans out to G sessions. Each session is a state machine across the gateway's worker pools. Terminal status: COMPLETED · ERROR · TIMEOUT.

1 INIT

Capacity-limited by max_init_workers.
  • start runtime container
  • bind-mount /polar/session
  • execute RuntimeSpec.prepare
  • timeout budget starts here

2 READY

Queued; waits for a run slot. Time queued is not charged.
  • completion records cleared
  • session pinned in registry
  • proxy env prepared

3 RUNNING

Capacity-limited by max_run_workers.
  • harness setup()
  • harness run_steps() exec inside container
  • agent's LLM calls flow through proxy → inference → capture

4 POST-RUN

Capacity-limited by max_postrun_workers.
  • builder: CompletionSession → Trajectory
  • evaluator: EvalResult (outcome / per-trace reward)
  • merge reward onto Trace.reward
  • tear down runtime · POST /callbacks/session_result
Builders registered by name: per_request, prefix_merging. Evaluators: session_completed, test_on_output, swebench_harness. Either can also be passed as module:Class.

3 · How a GRPO batch is built (slime_bridge)

One Polar Trajectory may have multiple Traces — typical with the per_request builder, where each agent ↔ model turn becomes its own trace. The bridge keeps every trainable trace as its own Slime Sample but normalizes reward at trajectory granularity, then broadcasts the advantage back to every trace of that trajectory.

B · Per-trajectory reward (one value per session)
Group 0 — raw rewards first reward per (g_idx, idx) wins
traj (0,0)3 traces · t0/t1/t2+1.0ok
traj (0,1)2 traces · t0/t10.0ok
traj (0,2)4 traces+1.0ok
traj (0,3)1 traceexclFAILED
valid trajectories: (0,0) (0,1) (0,2)
μg=0 = (1.0 + 0.0 + 1.0) / 3 = 0.6667
σg=0 = stdev{1.0, 0.0, 1.0} ≈ 0.5774
# GRPO advantage per trajectory:
A(0,0) = (1.0 − μ) / (σ + ε) = +0.577
A(0,1) = (0.0 − μ) / (σ + ε) = −1.155
A(0,2) = (1.0 − μ) / (σ + ε) = +0.577
A(0,3) = 0 # FAILED → forced 0, excluded from μ/σ
std_norm only when advantage_estimator ∈ {grpo, gspo} and grpo_std_normalization=true; otherwise just mean-center. If all members of a group fail, every advantage is forced to 0.

(group_index, index)
the key the post-processor groups by
The reward post-processor doesn't double-count: only the first reward per (group_index, index) contributes to μ/σ, even though every trace of that trajectory is its own Sample. Off-policy-stale groups are dropped before they reach this stage.
End-to-end ordering for one training step: Slime sampler → render_task_payload → POST /rollout/task/submit (one per group, async) → gateway pipeline (INIT→READY→RUNNING→POST-RUN per session) → session_result callback → session_result_to_samples (1 trace = 1 Sample) → post_process_rewards (per-group GRPO normalize) → Slime PPO/GRPO loss.
